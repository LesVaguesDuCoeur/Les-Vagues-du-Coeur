2. SYSTEME DE MOTS DE PASSE (4 MDP DISTINCTS)
================================================================================

L'application utilise 4 mots de passe différents, tous définis lors du setup :

1. MOT DE PASSE CONTACT
   - Accède à : page emergency.html (contacts d'urgence)
   - C'est aussi le "mot de passe secondaire" demandé pour vault et testament
     quand on y accède directement depuis la page d'accueil

2. MOT DE PASSE ADMIN
   - Accède à : page admin.html (panel d'administration complet)
   - L'admin peut ensuite naviguer vers toutes les pages SANS re-saisir de mdp

3. MOT DE PASSE VAULT (Mes Infos Privées)
   - Accède à : page vault.html (fiche personnelle)
   - Depuis la page d'accueil : si ce mdp est saisi, redirection vers vault.html
     MAIS une fenêtre s'ouvre d'abord demandant :
       → Nom complet OU Nom de la société
       → Mot de passe CONTACT (le mdp n°1)
   - Ces infos sont envoyées par email (alerte d'accès d'urgence)

4. MOT DE PASSE TESTAMENT
   - Accède à : page testament.html
   - Depuis la page d'accueil : si ce mdp est saisi, redirection vers testament.html
     MAIS une fenêtre s'ouvre d'abord demandant :
       → Nom complet OU Nom de la société
       → Mot de passe CONTACT (le mdp n°1)
   - Ces infos sont envoyées par email (alerte d'accès d'urgence)

STOCKAGE DES HASH :
- Les hash SHA-256 des 4 mots de passe sont stockés dans Google Sheets
- Champs : contactHash, adminHash, vaultHash, testamentHash
- Les mots de passe eux-mêmes servent de clé de chiffrement AES

4. CHIFFREMENT (crypto.js)
================================================================================

ALGORITHME : AES-GCM (Web Crypto API native du navigateur)
DERIVATION DE CLE : PBKDF2 (SHA-256, 100 000 itérations)
SEL : Généré aléatoirement (16 octets) pour chaque opération
IV : Généré aléatoirement (12 octets) pour chaque opération

PROCESSUS DE CHIFFREMENT :
1. Le mot de passe est converti en clé via PBKDF2
2. Un sel et un IV aléatoires sont générés
3. Les données sont chiffrées avec AES-GCM
4. Le résultat est encodé en base64 : sel + iv + données chiffrées

PROCESSUS DE DECHIFFREMENT :
1. Le base64 est décodé
2. Le sel (16 premiers octets) et l'IV (12 octets suivants) sont extraits
3. La clé est dérivée du mot de passe avec PBKDF2 + le sel
4. Les données sont déchiffrées avec AES-GCM

TOUT EST CHIFFRE :
- Les contacts d'urgence
- Les données de la fiche personnelle (vault)
- Le testament
- Chaque section est chiffrée avec son propre mot de passe comme clé

5. BACKEND - GOOGLE APPS SCRIPT (Code.gs)
================================================================================

URL DU SCRIPT : (À définir lors du déploiement)
METHODE : doPost(e) - reçoit des requêtes POST en JSON

FONCTIONNALITES :
1. SAVE (action: 'save') :
   - Reçoit { action: 'save', data: payload }
   - Extrait payload.data si payload.action === 'save' (unwrapping)
   - Sauvegarde les données chiffrées dans Google Sheets
   - La feuille contient une seule ligne avec toutes les données en JSON

2. LOAD :
   - Retourne toutes les données stockées en JSON
   - Les données restent chiffrées (le déchiffrement se fait côté client)

3. EMERGENCY ACCESS (action: 'emergencyAccess') :
   - Reçoit { action: 'emergencyAccess', name: '...', section: '...', timestamp: '...' }
   - Envoie un email d'alerte à l'adresse configurée
   - NE sauvegarde PAS les données (ne doit pas écraser la BDD)
   - L'email contient : qui a accédé, quelle section, quand

4. SETUP :
   - Initialise la structure de données dans Google Sheets
   - Stocke les hash des 4 mots de passe
   - Stocke l'email de notification

STRUCTURE DE DONNEES DANS GOOGLE SHEETS :
{
  "contactHash": "sha256...",
  "adminHash": "sha256...",
  "vaultHash": "sha256...",
  "testamentHash": "sha256...",
  "email": "user@example.com",
  "contacts": "données_chiffrées_base64",
  "vault": "données_chiffrées_base64",
  "testament": "données_chiffrées_base64"
}

6. API (api.js)
================================================================================

FONCTION PRINCIPALE : postToApi(payload)
- Envoie un POST JSON au Google Apps Script
- Si payload.action === 'emergencyAccess' → envoie directement (pas de wrapping)
- Sinon → wrappe dans { action: 'save', data: payload }
- Gère les erreurs réseau avec des messages utilisateur

FONCTION DE CHARGEMENT : loadFromApi()
- GET ou POST pour récupérer les données
- Retourne le JSON parsé

================================================================================

--- ADMIN.HTML ---
Panel d'administration.
- Login avec mot de passe admin
- Vue d'ensemble de toutes les sections
- Navigation vers contacts, vault, testament SANS re-saisir de mdp
- Options de gestion (modifier mdp, export, etc.)

--- VAULT.HTML ---
Fiche personnelle / Infos privées.
- Informations personnelles sensibles (à définir par l'utilisateur)

--- TESTAMENT.HTML ---
Testament numérique.

- Envoie une alerte email en cas d'accès direct (action: 'emergencyAccess')

9. ALERTES EMAIL
================================================================================

Quand quelqu'un accède au vault ou au testament depuis la page d'accueil :
1. Il entre le mot de passe vault/testament sur index.html
2. Une modal s'ouvre demandant nom + mot de passe contact
3. Si le mdp contact est correct :
   - Une alerte email est envoyée via le backend
   - L'email contient :
     → Qui : le nom saisi
     → Quoi : quelle section (Fiche Personnelle ou Testament)
     → Quand : date et heure
   - L'utilisateur est redirigé vers la page correspondante
4. Si le mdp contact est incorrect → erreur (toast)

L'email d'alerte est envoyé à l'adresse configurée lors du setup.

10. SECURITE - REGLES IMPORTANTES
================================================================================

- TOUT est chiffré côté client avant envoi au serveur
- Le serveur ne voit JAMAIS les données en clair
- Les mots de passe ne sont JAMAIS stockés en clair (uniquement les hash SHA-256)
- Les mots de passe servent de clé de chiffrement AES-GCM
- Pas de session serveur → tout est en sessionStorage côté client
- sessionStorage est vidé à la fermeture de l'onglet
- JAMAIS de alert(), confirm(), prompt() natifs → utiliser les modals custom
- Pas de console.log des données sensibles en production

13. BUGS CORRIGES (HISTORIQUE)
================================================================================

Ces bugs ont été identifiés et doivent être évités dans la reconstruction :

1. Les mots de passe vault et testament ne fonctionnaient pas depuis la page
   d'accueil → Corrigé : le hash est comparé correctement à vaultHash et
   testamentHash dans les données retournées par l'API

2. Les bulles natives (alert/confirm/prompt) apparaissaient → Corrigé : tout
   remplacé par des toast/modal custom via utils.js

3. L'admin devait re-saisir les mdp pour accéder aux sous-pages → Corrigé :
   sessionStorage.adminKey bypass les formulaires de login des sous-pages

4. Le payload emergencyAccess était traité comme un save et écrasait la BDD
   → Corrigé : Code.gs vérifie action === 'emergencyAccess' et ne sauvegarde pas

5. api.js wrappait tous les payloads, y compris emergencyAccess → Corrigé :
   les payloads avec action: 'emergencyAccess' ne sont pas wrappés

6. vault.js cachait le .login-box entier avec parentElement.style.display
   → Corrigé : re-render complet du innerHTML de .login-box
